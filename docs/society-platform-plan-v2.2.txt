1. event_role_history (046) - SCHEMA AND INTEGRATION DESIGN
=====================================================================

1.1 The question it answers
   "Which role did this person previously hold on this event, and when did that role end?"
   Three tables, three jobs, never mixed:
     event_members       roles held NOW
     event_role_history  roles held BEFORE, and when they ended          <- new
     audit_log           WHO made the change
   Identity is user_id throughout. Two people both called "Rohan" are two people; one person who corrects
   their name is still one person. Nothing is de-duplicated by display name anywhere in this design.

1.2 Schema (supabase/migrations/046_event_role_history.sql)
   id, event_id, user_id, role (the role that ended), became_role (null = removed), started_at (best
   effort), ended_at, ended_by (nullable), end_reason (removed | role_changed | society_removed |
   audit_backfill), source (trigger | audit_backfill), created_at.
   RLS on, zero policies, service-role access only - same as every table since 009.
   You suggested id, event_id, user_id, role, started_at, ended_at, ended_by, end_reason, created_at.
   Differences, and why: became_role (a demotion and a removal are different events, and the credits
   want to know which); source (rows recovered from the audit log are marked as such); started_at is
   nullable because only event_members.created_at can supply it and audit-recovered rows have none.

1.3 How it is written: a trigger on event_members
   I recommend a database trigger over writing history from each API route. Every way a role can end passes
   through event_members, and the app currently has several: Settings removal (DELETE), a role change
   (the POST upsert), an access request approved over an existing role (api/access-requests.ts also
   upserts), and the planned society removal. A trigger covers all of them - and manual SQL - in the same
   transaction as the change, so there is never a removal without its history, and the next route someone
   writes cannot forget it. The cost is that the trigger does not know WHO acted; audit_log does, and
   remains the authority. A SQL function (below) can pass the actor in through a transaction setting.

   Coverage of the four paths you listed:
     1. Member removed from Event Settings      DELETE /api/event-members  -> trigger, no API change
     2. Event Admin removed or demoted          POST (role change) / DELETE -> trigger, no API change
     3. Event Committee removed or demoted      same
     4. Society membership removal that revokes event access   -> remove_society_member() (1.5)
   Also covered for free: access-request approvals that change a role; role changes made in SQL.
   A role "re-saved" unchanged (page access edited) writes nothing.
   Deleting an event or an account does not write history (there is nothing left to describe).

1.4 Closing credits (api/_lib/closing.ts) - the read side
   Today: core = event_members with role admin/committee, admin first then committee then alphabetical,
          merged with the hand-typed extra_core, ordered by the committee's core_order.
   Proposed: core = the union, BY user_id, of
          (a) current event_members with role admin/committee, and
          (b) event_role_history rows whose role (the role that ENDED) is admin/committee.
   - One entry per person. Their tier is the HIGHEST role they ever held on the event (admin > committee),
     so the Admin-before-Committee order is preserved. DECISION 1 below.
   - A former read-only member is never added; neither is somebody whose only history is read_only.
     A resident promoted to committee and later removed IS credited (they held committee).
   - Names come from app_users at read time (the person's current display name), never copied, never
     matched by name. extra_core, volunteers, prasad, sponsors and contributors are untouched.
   - Names only: no email, no flat, no role label shown, no "former" marker - same as today's public card.
   - If the table does not exist (046 not run) the read treats history as empty and the page is exactly
     today's. This code is NOT written yet; I will write it only after you approve this design and report
     046 as applied.
   - Society Management's roster is a different surface and is not affected.

1.5 Society member removal (B7) - design only, depends on 046 AND 042
   One SQL function, remove_society_member(p_org, p_user, p_actor), one transaction:
     - sets app.actor and app.role_end_reason = 'society_removed' for the transaction,
     - deletes the person's event_page_permissions and event_members rows for EVERY event of that society
       (the trigger records each ended role into history),
     - deletes their organization_members row (042's trigger refuses it if they are the last society admin),
     - returns how many event roles ended.
   Nothing the person recorded is touched: contributions, expenses, comments, registrations, auction bids,
   tasks and photographs are the event's history, not their membership - the same rule the Settings roster
   already states. Their registered household bookings are not cancelled.
   The Members tab gets a Remove button with a confirmation that lists, before anything happens: the roles
   they hold on events ("Admin of Garba Night, Committee of Ganesh Chaturthi"), and a WARNING for any event
   where they are the ONLY event admin (society admins still administer it, but the committee should know).
   Audit: one society_member delete row plus one event_member row per ended role, sharing a request id.
   DECISION 2 below (what removal does to event roles) - you wrote "revoking event access", so that is the
   design; say if you want it optional.

1.6 Recovering the past (optional)
   Endings before 046 are not in event_members, but audit_log has recorded every removal and role change
   since 030. docs/migration-notes/046_event_role_history.txt section 4 has a read-only "look first" query
   and an idempotent recovery, tested on scratch data. It is a separate step, run only if you want it.

1.7 Decisions I need on 046
   D1. A person who held admin and was later demoted to committee (or removed): credit them in the ADMIN
       tier ("highest role ever held" - my recommendation, because credits record service) or in the tier
       of their CURRENT role only?
   D2. Should removing a society member always revoke their event roles (as written), or ask the admin?
   D3. Show a small "former" marker on credits for people who no longer hold a role? (Recommended: no.)
   D4. Run the audit recovery (1.6) at all?

2.1 Migration 043 (prepared; do not run until you have reviewed it)
   supabase/migrations/043_event_proposals.sql, notes in docs/migration-notes/043_event_proposals.txt

   - Table event_proposals: the proposal's own copy of the event fields (name, type, template, unit label,

     creates nothing; a rejected proposal cannot become an event; approval creates exactly one draft
     with the proposer as admin and the proposal linked; a second approval is refused.

   under the existing rules (say if publishing should also need a society admin); a society admin may
   approve their own proposal; the 40-event creation cap is not applied to approval; new events have no
   slug until the admin sets one (same as every draft today).

3. 045 - PLATFORM ACTIVITY DATA: THE MODEL I WOULD PROPOSE  (design only; no SQL, no migration)
=====================================================================

3.1 The question you asked
   Can the existing event_visits / event_page_views be generalised, or are new platform tables genuinely
   necessary - and how do we avoid two tables collecting different versions of the same traffic?

   My answer: GENERALISE THE EXISTING TWO TABLES. New platform tables are not necessary, and v2.1's
   "new tables plus a union view" is withdrawn. Reasons:
     - Both existing tables already hold exactly what a platform needs: visitor_key, user_id, started_at,
       last_seen_at, page_key, page_views, coarse device/browser/country/city, and per-page dwell. The only
       thing that ties them to events is event_id NOT NULL and the cascade on it.
     - One heartbeat, one write, one set of privacy rules. A second pair of tables would either double the
       writes on the app's hottest path or need a view that papers over two definitions of "a visit".
     - No history is lost and no existing read changes: every existing row is an event visit, and the
       Traffic read filters by event_id as it does now.
   What generalising changes (the actual 045 shape, for approval before any SQL is written):
     event_visits       + surface text not null default 'event'
                        + organization_id uuid null  (-> organizations, on delete set null)
                        event_id: NOT NULL dropped; FK changed from "on delete cascade" to "on delete
                        set null" so platform history survives an event being deleted (today deleting an
                        event silently deletes its traffic)
     event_page_views   same three changes
     app_users          + last_seen_at timestamptz null (3.6)
     indexes            (organization_id, started_at), (surface, started_at)
     existing rows      organization_id filled once from events.organization_id; surface = 'event'
   The names stay "event_*": renaming a hot table in a live app means a window where deployed code and
   schema disagree, for a cosmetic gain. A comment on each table records that it now holds every surface.
   Adding nullable / constant-default columns is a metadata change in PostgreSQL 11+, not a table rewrite.
   DECISION 5: confirm "generalise, do not duplicate".

3.2 Visit model
   A visit = one browser tab session, one row (id held in sessionStorage, as today). A new tab or a
   reopened browser is a new visit. visitor_key = a random value the browser keeps (localStorage); it
   groups repeat visits and identifies nobody. user_id is set only when signed in. The same visitor_key
   is used on every surface, which is what makes "unique visitors across the society" answerable.
3.3 Session model
   There is no separate session table. The visit IS the session. A "browsing session" in the analytics
   sense (activity separated by 30 minutes of silence) can be derived at query time from a visitor's
   visits if it is ever needed; it is not stored, so there is nothing to keep in step.
3.4 Page-view model
   One row per page opened within a visit (event_page_views, generalised), with page_key, opened_at,
   left_at, seconds. page_key comes from a fixed server allowlist per surface, never free text.
   Surfaces (allowlist): event, society_home, society_admin, profile, event_proposal, login.
   Scope: organization_id and event_id are resolved and verified ON THE SERVER; the browser never gets to
   assert them. event surface -> event_id set, organization_id derived. society surfaces -> organization_id
   set, event_id null. login/profile -> neither.
3.5 Heartbeat and last_seen_at (of a VISIT)
   Same endpoint (api/event-access.ts ?resource=traffic, still importing only page-visibility and server):
   eventId becomes optional and a surface is accepted. A visit row's last_seen_at is the time of its latest
   heartbeat while the tab is visible; "time spent" = last_seen_at - started_at, approximate and under-
   counting by up to one beat (no unload beat is possible), exactly as the panel says today. Throttles
   (20 s per page) and "a different page always counts" are unchanged.
3.6 app_users.last_seen_at (of a PERSON) - a different thing with a similar name
   Meaning: the last time the server saw an authenticated application request from this person. It is
   application activity, not login time, not session length, not "online now".
   Updated by: any /api request whose Firebase token the server verified (requireAppUser / optionalAppUser
   with a valid token), including a signed-in visible-tab heartbeat. NOT by: no/invalid token, link
   crawlers, server work.
   Throttle: at most one write per person per hour, enforced in SQL so it holds across serverless
   instances (update ... where last_seen_at is null or last_seen_at < now() - interval '1 hour').
   Fire-and-forget; it never delays or fails a request; silent if the column is absent.
   Readable by: nobody in the product. Platform analytics only (future). Never by society or event admins.
3.7 Identity / who can read what
   The same rows serve two readers, separated by the API, not by table: a society admin reads their own
   society's rows (Traffic, moved into Society Management later); the platform owner reads across
   societies (future Control Center). Names appear only for signed-in visitors, as today. No IP address is
   stored, raw or hashed. Coarse device/browser/city only. No per-click paths.
3.8 Retention
   Nothing is deleted today (F1 removed the 90-day delete; 90 days is only the display window). Row count
   is per VISIT, not per beat, so volume is small (a society of ~500 households is on the order of tens of
   thousands of visit rows a month). My assumption for a future policy, NOT implemented and not decided:
   keep raw rows ~13 months, rolling them into daily per-society aggregates first, and only delete rows
   that have been rolled up. Deleting anything needs your explicit decision; the aggregation must exist
   before the deletion does.
3.9 Behavioural / product events - still DESIGN ONLY
   Unchanged from v2.1 section G: a separate small allowlisted stream (platform_events) for a handful of
   named actions, never a clickstream, no free text, nothing collected until you approve the allowlist.
   audit_log stays for business actions. Nothing here is built.
3.10 Not decided / to verify before 045 SQL is written
   - Who may send a beat for a society surface: I would require that the society exists and that the
     caller could open that page (the same check Society Home uses), so a stranger cannot write rows into
     a society's stream.
   - The size of event_visits / event_page_views in production (a one-line count you can run) - to confirm
     the one-time organization_id backfill is small.
   - Whether to keep "event_*" table names (recommended) or rename later in a quiet window.
