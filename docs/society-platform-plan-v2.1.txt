C. B7 (MEMBER REMOVAL) - CLOSING-CREDIT AUDIT  [HELD - STOP, PROPOSAL BELOW]
=====================================================================

I audited api/_lib/closing.ts (sendClosingPayload) and the closing schema (014, 020).
B7 is NOT implemented. Below is exactly how credits are derived.

 CREDIT GROUP        DERIVED FROM                                   EVENT ROLE INVOLVED
 ------------------  ---------------------------------------------  ------------------------------------
 Core committee      event_members WHERE role IN ('admin',          admin and committee are both put in
 ("core")            'committee'), ordered admins-first then        this ONE list. read_only members are
                     alphabetical, then MERGED with the hand-kept   never credited. The page does not
                     event_closing.extra_core names, then put in    say which of the two a person was -
                     the committee's own core_order if one exists   only the ORDER shows it.
 Volunteers          tasks.owner_name + event_schedule.owner_name   none (free-text names, not members)
                     (free text) + hand-kept extra_volunteers
 Prasad sponsors     prasad_items arrangers (free text names)       none
 Sponsors            sponsors table                                 none
 Contributors        contributions + residents                      none
 Auction winners     auction bids -> app_users name                 none
 Reviewers / photos  event_feedback.user_id / gallery created_by    none
 Shout-outs          hand-kept                                      none

 What removing ACCESS does to credits:
   - An event_members row with role admin or committee is deleted  -> the person DISAPPEARS from the
     "core committee" credits of that event (this already happens today when an event admin removes
     a member in Settings).
   - A read_only member: no credit effect.
   - Every other group is untouched - they are not role-based.
   - Contributions, expenses, comments, registrations, gallery, reviews, tasks and the audit log
     reference app_users(id), not event_members, so they are unaffected by deleting access rows.

 Why simply appending removed people to event_closing.extra_core is NOT clean:
   1. It FLATTENS the role: the page orders admins before committee; a name in extra_core is
      appended at the end, so the admin/committee distinction that the order carried is lost.
   2. It MIXES TWO MEANINGS: extra_core means "somebody who did the work but is not a member row,
      typed in by hand". A former member would become indistinguishable from a hand-typed name, and
      the credits editor shows hand-typed names as removable - so a later tidy-up can silently delete
      a real organiser's credit.
   3. It stores a NAME, not the person: no link to app_users, so a later rename or a duplicate name
      cannot be resolved.
   4. It needs an event_closing row to exist for EVERY event of the society - creating rows as a side
      effect of removing a person.
   5. It applies to events that are not finished. Should somebody removed from an event that is still
      being planned appear in credits that do not exist yet? That is a policy question, not a
      mechanical one.
 Conclusion: the current closing schema cannot preserve historical attribution WITHOUT changing the
 meaning of an existing field. Per your instruction I stopped before B7.

 SMALLEST CLEAN SOLUTION (proposal, needs your approval):  046_event_role_history
   A new, additive table written at the moment event access ENDS:
     event_role_history(
       id bigserial pk,
       event_id        uuid -> events (cascade),
       organization_id uuid -> organizations (set null),
       user_id         uuid -> app_users (set null),
       display_name    text not null,        -- the name as credited at the time
       role            event_role not null,  -- admin | committee | read_only
       ended_at        timestamptz not null default now(),
       ended_by        uuid -> app_users (set null),
       reason          text not null         -- 'society_member_removed' | 'event_member_removed'
     )
   RLS on, zero policies (project rule). Nothing existing changes meaning.
   - Closing credits "core" = current admin/committee members  UNION  history rows with role
     admin/committee for that event, de-duplicated by user_id, ordered admin-before-committee exactly
     as today. extra_core keeps meaning "hand-typed". The credits editor can mark them "Former member".
   - It fixes the SAME credit loss that already happens when an event admin removes a member in
     Settings (that route would write the history row too).
   - It is a role history the platform analytics will want anyway (who held which role, until when).
   - B7 then = (1) insert history rows for the person's admin/committee event roles, (2) delete their
     event_members + event_page_permissions rows for that society's events, (3) delete the society
     membership, (4) audit entry - all done by ONE SQL function (atomic) once 046 exists, so a
     failure half-way cannot leave a person with half their access.
   Alternative (not recommended): add a revoked_at column to event_members and filter it in every
   access check - dozens of queries would need the filter; one missed query leaves revoked access live.

 Decision for you:  approve 046_event_role_history (and B7 built on it), or choose another approach.

E. PROPOSED GENERAL PLATFORM VISIT / SESSION / PAGE MODEL  (for review - 045 NOT finalized)
=====================================================================

Goal: represent Society Home, event pages, profile, event creation / proposal, login and
future surfaces - without treating Society Home as "an event visit with no event".

 Today (unchanged by this proposal):
   event_visits       one row per visit, event_id NOT NULL, page_key, page_views, coarse device/browser/geo
   event_page_views   one row per page opened + dwell, event_id NOT NULL

 PROPOSED NEW TABLES (names provisional):

   platform_visits                      -- one row per browser-tab visit, ANY surface
     id            uuid pk              (client-generated, held in sessionStorage, like event_visits)
     visitor_key   text not null        (random, browser-held; identifies nobody; groups guests)
     user_id       uuid null -> app_users (set null)
     started_at    timestamptz not null default now()
     last_seen_at  timestamptz not null default now()
     surface       text not null        -- 'society_home' | 'event' | 'profile' | 'event_proposal'
                                        -- | 'society_admin' | 'login' | ... (server allowlist)
     organization_id uuid null -> organizations (set null)    -- null for e.g. login
     event_id        uuid null -> events (set null)           -- only when surface = 'event'
     page_views    integer not null default 1
     device, browser, country, city   text null   (coarse, exactly as event_visits; NO IP, ever)

   platform_page_views                  -- the page-level detail + dwell time
     id            bigserial pk
     visit_id      uuid not null        (not a FK, like event_page_views - a page view must never fail)
     user_id       uuid null
     surface       text not null
     page_key      text null            -- 'dashboard', 'members', 'overview', ...
     organization_id uuid null, event_id uuid null
     opened_at timestamptz default now(), left_at timestamptz null, seconds integer null

 Relationship with the existing tables:
   - event_visits and event_page_views KEEP being written exactly as today for event pages.
     Nothing about the Traffic read, the heartbeat or the history changes, and no history is lost.
   - The new tables record every surface going forward. To avoid doubling writes on the hottest
     route, an event-page beat is NOT written twice. A read-only VIEW (platform_visits_all) unions
     platform_visits with event_visits (mapped to surface = 'event') so platform analytics sees one
     stream. (If you prefer one canonical table, the alternative is a one-time INSERT...SELECT of the
     old rows and then dual-write for a while - more moving parts, more risk. Not recommended.)
   - Same endpoint (api/event-access.ts ?resource=traffic): `eventId` becomes optional and a `surface`
     is accepted. It keeps importing only page-visibility and server (cold-start rule). The server
     validates the surface against an allowlist and verifies any society/event scope the caller
     names; scope is never trusted from the browser.
   - Society Home is a first-class surface: organization_id set, event_id null. No event involved.

 Privacy: same rules as today - no IP stored raw or hashed; coarse device/browser/city only;
   guests stay guests; user_id only when signed in; no per-click paths. Surfaces and page_keys come
   from a fixed list, never from free text.

 Definitions that go with it (so metrics are never faked):
   visit    = one browser tab session, one row; ends when beats stop (no unload beat is possible)
   page view= one page_key opened within a visit
   active   = see section F (application activity), NOT presence on a page
   time spent is APPROXIMATE (last beat - first beat; under-counts up to one beat interval)

 Decision for you: approve this shape (and the "union view, no dual write" choice) before I write 045.

F. D3 - app_users.last_seen_at  (DEFINITION, to be created by 045)
=====================================================================

 Meaning: the last time the server saw an authenticated APPLICATION REQUEST from this user.
 It is application activity, NOT login time, not a session length, and not "online now".

 What updates it (exactly):
   - Any request to the app's /api/* routes that carries a valid Firebase token which the server
     verified (the requireAppUser and optionalAppUser paths), including the visibility heartbeat
     of a signed-in visitor on a visible tab.
 What does NOT update it:
   - Requests with no / invalid token; link-preview crawlers (they send no token);
     server-to-server work; the browser's own background refetches are included only because
     they carry a token - they are rare and bounded by the same throttle.
 Throttle: at most ONE write per user per hour, enforced in SQL so it holds across serverless
   instances:  update app_users set last_seen_at = now()
               where id = :user and (last_seen_at is null or last_seen_at < now() - interval '1 hour')
   Fire-and-forget (never delays or fails the request), degrades silently if the column is absent.
 Who can read it: nobody in the product. Platform analytics only (future). Never shown to users,
   society admins or event admins.
 Why now: it cannot be reconstructed after the fact, and "active users today/week/month" depends on it.

G. D5 - BEHAVIOURAL EVENTS  (DESIGN ONLY - nothing is collected)
=====================================================================

 Principle: audit_log is for BUSINESS ACTIONS (who changed what). Behavioural/product events are a
 separate, small, allowlisted stream. This is NOT a clickstream; page views already exist.

 Proposed table (not created):
   platform_events( id bigserial pk, occurred_at timestamptz default now(), name text not null,
                    user_id uuid null, organization_id uuid null, event_id uuid null,
                    surface text null, props jsonb null )
   - `name` must be in a SERVER allowlist; anything else is rejected, not stored.
   - props: a small fixed set of enum/integer fields per name. No free text, no names, no other
     people's ids, max 5 keys.

 Initial allowlist (candidates only - none collected until you approve):
   pass_shared            organiser shared a pass          (props: channel = share|download)
   wristband_printed      organiser printed wristbands     (props: count bucket)
   calendar_added         resident added to calendar       (props: kind = single|picks)
   event_shared           resident used Share              (props: channel)
   registration_started   resident opened the booking form (props: none)   [completion is already a row]
   society_invite_used    code join (already audited - listed only to avoid double counting)
 Explicitly NOT collected: clicks, hovers, scrolls, search text, form contents, typing, mouse paths,
   anything that identifies what a person looked at beyond the page_key already recorded.
