0. HEADLINE FINDINGS FROM THE AUDIT (read these first)
=====================================================================

 F1. TRAFFIC HISTORY IS BEING DELETED.  [BUILD NOW - code fix]
     api/_lib/traffic.ts deletes every event_visits row older than 90 days, across
     ALL events, each time any admin opens the Traffic panel (a "retention" step on
     the read). So the visit-level history (devices, browsers, cities, repeat
     visitors, visit duration) that a future Platform Control Center needs is
     already being thrown away. Fix: stop the delete now. (Per-page history in
     event_page_views and the audit log are kept forever, so those are fine.)
     Removing the Traffic card from Settings also stops that read, but the delete
     must be removed explicitly so it cannot return when the read moves.

 F2. audit_log ALREADY HAS THE RIGHT SCOPE COLUMNS.  [EXISTS / REUSE]
     It has event_id AND organization_id (both nullable), actor, action,
     entity_type, entity_id, summary, changes jsonb, request_id. api/_lib/audit.ts
     already resolves organization_id from the event at write time. So NO
     scope_type/scope_id model is needed and nothing needs to be squeezed into
     entity_id. We only add missing audit CALLS (society join, role changes,
     proposals) and one index.

 F3. A REQUIRE-SOCIETY-ADMIN CHECK ALREADY EXISTS, BUT IS PRIVATE.  [EXISTS / REUSE]
     requireSocietyAdmin() is a private helper inside api/_lib/societies.ts, and
     authority.ts has isSocietyAdmin(). We consolidate them into ONE exported
     requireSocietyAdmin() in authority.ts and use it for every society-management
     route. An event admin alone does not satisfy it.

 F4. EVERY CURRENT EVENT ADMIN IS PROBABLY A SOCIETY ADMIN.  [BUILD NOW - pre-check]
     Migration 023's backfill made everyone with a role on an event a member of that
     event's society carrying the SAME role, choosing admin where they had several.
     So existing event admins were promoted to society admins. Before the new page
     goes live we run a pre-check listing each society's admins so you can confirm
     that is what you want, and demote anyone who should not have society-wide access.

 F5. A MEMBER'S FLAT/UNIT IS A PRIVATE PROFILE FIELD.  [DECISION NEEDED]
     The only place a person's flat lives is app_users.flat (migration 041), and
     the product promises it is "private: returned to its owner and nobody else".
     Showing it in the Society Admin roster changes that promise. See decision D1.

 F6. REMOVING SOMEONE FROM A SOCIETY CAN ERASE THEIR CREDIT.  [BUILD NOW - design]
     The closing page derives the "committee" credits from event_members. If we
     revoke event access by deleting event_members rows, those people vanish from the
     credits of past events. The existing manual-credit list (event_closing.extra_core)
     is the mechanism built for exactly this, so removal must snapshot their name
     into it BEFORE deleting access. See section 3.

 F7. THERE IS NO SOCIETY-LEVEL ACTIVITY TRACKING FOR ANYTHING OUTSIDE AN EVENT.
     Visits to the Society home, login, profile and new-event pages are not tracked
     (the heartbeat only runs inside an event). Sign-in time / "last active" is not
     stored anywhere. These cannot be reconstructed later. See sections 8 and 9.

3. MEMBER REMOVAL - ACCESS VERSUS HISTORY                         [BUILD NOW]
=====================================================================

Principle: ACCESS and HISTORICAL ATTRIBUTION are different things.

Schema audit (what removal can and cannot touch):
 - organization_members is a plain join table. Nothing else has a foreign key
   to it, so deleting a row only removes society membership.
 - event_members and event_page_permissions are the access tables. History tables
   (contributions, expenses.submitted_by/settled_by, registrations,
   task_comments/task_assignees, event_gallery_*, event_feedback, audit_log, etc.)
   reference app_users(id), NOT event_members, so deleting access rows does not
   delete or orphan any history.
 - EXCEPTION (finding F6): closing-page committee credits are derived from
   event_members. Deleting the row would drop the person from the credits.

Removal behaviour:
   1. Snapshot credit: for every event of the society where the person holds an
      event role and the event has (or may have) closing credits, append their
      display name to event_closing.extra_core (existing manual-credit list,
      de-duplicated by name; this is what that field is for).
   2. Revoke access: delete their event_members and event_page_permissions rows
      for that society's events, and any open access request.
   3. Delete their organization_members row (society membership).
   4. Write an audit entry (who removed whom, from which society, what was
      revoked).
   NEVER touched: contributions, registrations, expenses, comments, gallery,
   reviews, tasks, audit entries, organizer credits, historical actions.
   Their app_users account is untouched; they can be re-invited later.
   Confirmation dialog states: "X will lose access to the society and N events.
   Everything they recorded stays." and warns if X is the only admin of an event
   ("society admins will still be able to manage it").
   Until migration 043, steps run in API order (credits -> events -> society) and
   are not atomic; a SQL function reinforces this later. We say so plainly in code
   comments and do not claim atomicity.

4. LEVEL 2 - EVENT PROPOSAL LIFECYCLE                            [BUILD NOW]
=====================================================================

   Resident (society member)
        |  Propose event  (name, type, short description, proposed date(s),
        |                  venue, optional note)
        v
   PENDING  --(Society Admin reviews)-->
        |-- Approve ........ -> APPROVED -> normal event created as a DRAFT
        |-- Request changes  -> CHANGES REQUESTED (note shown to proposer;
        |                      proposer edits and resubmits -> PENDING)
        |-- Reject .......... -> REJECTED (final, reason shown)
        |-- Discard ......... -> ARCHIVED (soft; confirmation required; hidden
        |                      from queues; row kept for audit)
   Proposer may also WITHDRAW their own pending proposal (-> ARCHIVED).

   APPROVAL NEVER PUBLISHES. Approval creates a Draft event; the organizer
   configures it with existing tools and explicitly publishes when ready.
   Publishing keeps its existing readiness checks.

   Proposer experience (no need to contact an admin):
     "Pending society approval"
     "Changes requested: <note>"   [Edit & Resubmit]
     "Approved - Continue setting up event ->"  (links to the new draft)
     "Rejected: <reason>"
   Shown on the Society home as a private "Your proposals" shelf (only the
   proposer sees their own) and in the proposer's account area.

   Who becomes event admin of the approved event: the proposer (so they can
   configure and publish). Society admins are admins of every event regardless.

   Proposal form is deliberately small. It does not ask the proposer to configure
   modules. Event types/templates reuse the existing set (festival, sports,
   cultural, mixed, custom) - see section 6.

   Draft visibility [BUILD NOW]: because proposals live in their own table (section
   5), they never appear in event lists, the Society home, switchers, dashboards,
   finance, traffic or link previews. Approved drafts follow the existing draft
   rule (visible to society admin/committee and their own event roles only).

5. DATA MODEL: event_proposals TABLE  vs  approval_status ON events
=====================================================================
>>> THIS IS THE STOP POINT. Nothing is migrated until you approve a choice. <<<

Option A - approval_status (and related columns) on events
Option B - dedicated event_proposals table; an events row is created only on approval

What the code audit found:
 - `events` is read in MANY places, each filtering drafts its own way: society home
   (status_override='draft' hidden unless manager), event switcher / my-events
   (via event_members), event data, publication access, link previews (og), resolve,
   duplicate, command centre, traffic, closing, finance. Adding "pending/rejected"
   rows means every one of them must be taught a new state. One missed filter leaks
   a proposal into a public surface or pollutes counts.
 - A rejected/discarded proposal would become a permanent junk events row with
   modules, registration settings, finance tables and a traffic target.
 - create_event_draft (migration 033) ALREADY inserts events + event_members +
   event_page_visibility + event_registration_settings atomically, and refuses
   members who are not admin/committee - so a resident cannot use it today.

Comparison:

   Concern                               | A: status on events          | B: event_proposals table
   --------------------------------------+------------------------------+------------------------------
   Pollutes normal event queries         | YES - must filter everywhere | NO - separate table
   Rejected/discarded rows               | stay as fake events          | stay as proposals only
   Risk of leaking a pending proposal    | HIGH (many read paths)       | LOW (one new read path)
   Finance/traffic/dashboard pollution   | possible                     | impossible
   Cost of "draft" semantics             | overloads status_override    | event is a plain Draft on approval
   Proposal data that is not event data  | awkward extra columns        | natural (review note, version)
   Resubmit / request-changes cycle      | mutates a live-looking event | edits a proposal row
   Platform analytics on proposals       | mixed into events counts     | clean: proposals vs events
   Migration risk to existing events     | touches the events table     | touches nothing existing
   Atomic creation on approval           | n/a (row exists)             | one SQL function, one transaction
   Extra work                            | smaller migration            | one table + one function

RECOMMENDATION: Option B (event_proposals), exactly as you prefer.
   - A proposal is not an event. It becomes one only on approval.
   - It leaves every existing events query, module, finance and traffic path
     untouched, so it cannot regress anything live.
   - Approval runs one database function (approve_event_proposal) that locks the
     proposal row, checks it is still pending, creates the event Draft with its
     members and modules in one transaction, links proposal.event_id, and marks it
     approved. It does NOT call create_event_draft (which requires admin/committee
     membership); it performs the same inserts for the proposer.
   - Template modules: the template catalogue is client code today
     (src/data/event-templates.ts). The server must default modules for the
     approved event, so the pure catalogue data is moved to shared/ and re-exported
     (the file has one type-only import to remove).

Proposed table (for review - NOT final until approved):
   event_proposals(
     id uuid pk, organization_id -> organizations, proposed_by -> app_users,
     name, event_type, template_key, description, location, note,
     start_date, end_date, start_time, end_time,
     status ('pending'|'changes_requested'|'approved'|'rejected'|'archived'),
     review_note, reviewed_by -> app_users, reviewed_at,
     event_id -> events (set on approval), version int (optimistic concurrency),
     submitted_at, created_at, updated_at, archived_at )
   RLS on, zero policies (the project standing rule); all access via the API with
   the service role. Discard = archived_at (soft). No hard deletes.
   Lifecycle history is NOT a separate table: every transition writes an audit_log
   row (entity_type 'event_proposal', organization_id set), which also feeds future
   platform analytics (time-to-decision, approval rate).

   rollups (future platform_daily_rollups) so long-term trends survive any raw
